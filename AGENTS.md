# Руководство по репозиторию

Правила кода и архитектуры tg_stt_bot. Общее описание бота, конфигурации и запуска — в `README.md`.

## 1. Структура

- `cmd/app/main.go` — точка входа: флаг `-config`, `InitApp`, `RunApp`.
- `cmd/app/app/` — композиция приложения: `app.go` (структура `App`, `InitApp`, `RunApp`, closers),
  `config.go`, `logs.go`, `log_sink.go`, `providers.go`, `controllers.go`, `bot.go`, `errors.go`.
- `internal/configs/` — конфиг на cleanenv (файл + env), валидация, getter-API.
- `internal/models/` — чистые модели и функции без инфраструктурных зависимостей.
- `internal/providers/` — `errors.go` слоя провайдеров (пакет `providers`), общий для его подпакетов.
- `internal/providers/stt/` — HTTP-клиент parakeet.
- `internal/providers/telegram/` — Bot API: скачивание файлов, отправка сообщений и reply.
- `internal/controllers/` — `errors.go` слоя контроллеров (пакет `controllers`), общий для его подпакетов.
- `internal/controllers/chat-controller/` — сценарий расшифровки аудио.
- `internal/controllers/admin-controller/` — команды в личке админа.

`internal/app` в этом проекте не создаётся: это место под кодген gRPC-ручек, у бота long polling и ручек нет.

## 2. Правила слоёв

### 2.1 Только интерфейсы в конструкторах

- Структуры слоёв и их конструкторы принимают **только интерфейсы** и значения, никогда — конкретные типы
  других слоёв.
- Интерфейсы объявляются на стороне потребителя (в пакете, который их вызывает), а не рядом с реализацией.
- Конкретные структуры знает только вайринг: `cmd/app/app/providers.go` и `cmd/app/app/controllers.go`.
- Провайдеры и контроллеры не держат мутабельного состояния и безопасны для конкурентного использования:
  апдейты обрабатываются несколькими воркерами.

### 2.2 Один errors.go на слой

- У слоя ровно один `errors.go`, и **все** его сентинелы объявляются там — не по подпакетам:
  - `internal/controllers/errors.go` (пакет `controllers`) — ошибки chat- и admin-контроллера;
  - `internal/providers/errors.go` (пакет `providers`) — ошибки stt- и telegram-провайдера.
- Однопакетные слои держат свой `errors.go` рядом с кодом: `internal/configs/errors.go`,
  `internal/models/errors.go`, `cmd/app/app/errors.go`.
- Внутри подпакета слоя (`chat-controller`, `admin-controller`, `stt`, `telegram`) своего `errors.go`
  быть не должно: подпакет импортирует общий пакет слоя и оборачивает в его сентинелы
  (`controllers.ErrSendReply`, `providers.ErrSTTUnexpectedStatus`).
- Имена сентинелов уникальны в пределах файла слоя. У провайдеров они префиксованы внешним сервисом
  (`ErrSTTBuildRequest` / `ErrTelegramBuildRequest`, `ErrSTTUnexpectedStatus` /
  `ErrTelegramUnexpectedStatus`): одинаковые режимы отказа у stt и telegram — разные ошибки и
  сливаться в одну не должны.
- Ошибок «по месту» (`errors.New`/`fmt.Errorf` без сентинела) в коде слоя быть не должно.
- На границе слоёв ошибка обязательно оборачивается принимающим слоем: `fmt.Errorf("%w: %w", ErrXxx, err)`.
  Внутри слоя обёртки — по необходимости.
- `internal/models/errors.go` пустой по правилу слоя: чистые модели ошибок не возвращают.
- Исключение — контекстные префиксы шагов инициализации и closers в `cmd/app/app/app.go`: они добавляются
  поверх уже обёрнутых ошибок.

### 2.3 Метод на файл

- `controller.go` / `provider.go` — структура слоя, её интерфейсы-зависимости и конструктор.
- Каждый публичный метод — в отдельном файле (`transcribe.go`, `health.go`, `download_file.go`,
  `send_message.go`, `send_reply.go`, `handle_voice.go`, `handle_video_note.go`, `handle_command.go`).
- Приватные помощники выносятся в свои файлы, если так читается лучше (`do_request.go`, `redact.go`,
  `transcribe_and_reply.go`, `log_sink.go`).

### 2.4 internal/models

- Только чистая логика: без HTTP, без Telegram, без конфигов и логгера.
- Каждая структура со своими методами — в отдельном файле, поддиректории по необходимости.
- Общая логика двух контроллеров (разбивка текста, проверка допуска чата) живёт здесь, а не дублируется.

## 3. Инициализация и жизненный цикл

`InitApp` выполняет шаги строго последовательно и паникует на первой ошибке — половина бота не нужна:

1. config;
2. logs;
3. bot client (`bot.New`);
4. providers;
5. log sink;
6. controllers;
7. bot handlers (`RegisterHandlerMatchFunc`).

Порядок нетривиален и должен сохраняться: telegram-провайдер строится поверх `*bot.Bot`, поэтому клиент
создаётся до провайдеров; хендлеры регистрируются последними, потому что диспетчеры зовут контроллеры;
log sink — после провайдеров, потому что доставляет записи через telegram-провайдер.

Правила расширения:

- новый шаг добавляется в список `steps` в явном порядке и возвращает `error`, без panic внутри слоя;
- закрываемые ресурсы регистрируются через `addCloser(name, fn)`; `closeAll()` вызывает их в обратном
  порядке (LIFO) и агрегирует ошибки через `errors.Join`; точечное закрытие в произвольных местах не допускается.

## 4. Конфигурация

- Источники: JSON-файл, затем env поверх него; `.env` подхватывается в `internal/configs`.
- В потребителях — только getter-методы (`GetTelegramToken`, `GetSTTTimeout`, …). Прямой доступ к полям
  структуры конфига вне `internal/configs` не используется; контроллеры получают конфиг как интерфейс
  с нужными геттерами.
- Новый параметр добавляется сразу с json- и env-тегами, разумным дефолтом, getter-методом, валидацией
  в `validateConfig` (ошибка — сентинел из `errors.go`), строкой в `config.example.json`, строкой в таблице
  README и тестом.

## 5. Логи и сервисный чат

- Логирование — `slog` (JSON handler в stdout), уровень из конфига.
- Поверх базового хендлера стоит fan-out `serviceChatHandler`: записи уровня `ERROR` дополнительно уходят
  в сервисный чат через асинхронный `serviceChatSink`.
- Отправка не блокирует логирующего: очередь буферизирована, переполнение — дроп записи.
- Свои сбои sink пишет обычным `log` в stderr, **не через slog** — иначе рекурсия.
- Контроллеры и провайдеры про сервисный чат не знают: они возвращают ошибки, а диспетчеры в `bot.go`
  логируют их `slog.Error`.

## 6. Telegram и безопасность

- Токен бота **никогда** не попадает в текст ошибок и логов: URL скачивания файла содержит токен, поэтому
  ошибки транспорта редактируются (`redactToken` в провайдере и в `bot.go`).
- Апдейты из чатов вне whitelist игнорируются молча — решение принимает `models.IsChatAllowed`.
- Непойманные апдейты гасятся собственным default handler: библиотечный дефолт печатает каждый апдейт
  и утекает содержимое сообщений.
- Длина сообщения считается в UTF-16 code units (`models.SplitText`), не в рунах и не в байтах.
- Файлы больше 20 MB не скачиваются: `getFile` их не отдаёт.

## 7. Тесты

- **Каждое изменение кода сопровождается тестами** — юнит-тесты на новые и изменённые функции, и на успех,
  и на ошибочные сценарии. e2e-тестов в проекте нет.
- Контроллеры тестируются с ручными фейками их consumer-side интерфейсов, без библиотек моков.
- Провайдеры — через `httptest` (stt) и фейк интерфейса бота (telegram); обязателен тест, что токен
  не утекает в текст ошибки.
- `internal/models` — табличные тесты, включая эмодзи и астральные символы для UTF-16-счёта.
- `internal/configs` — env-переопределения через `t.Setenv` (cleanenv читает реальное окружение),
  отдельный кейс на каждую ошибку валидации.

## 8. Команды разработки

- `make lint` — `golangci-lint` по `.golangci.yml` (инструмент ставится в `bin/`).
- `make test` — `go test -count=1 ./...` с кешами в `.cache/`.
- `make format` — `go fmt ./...`.
- `make build` / `make run` — сборка бинарника в `bin/` и локальный запуск.
- `make tidy` — `go mod tidy`.

Перед коммитом должны проходить `make lint`, `make test` и `go build ./...`.

## 9. Стандарты кода

- Код форматирован `gofmt`/`goimports`; линтеры из `.golangci.yml` (включая `errorlint`, `bodyclose`,
  `nilerr`, `gosec`) должны быть зелёными, `nolint` — только с объяснением и конкретным линтером.
- Комментарии в коде — на английском, документация и планы — на русском.
- `context.Context` передаётся сверху вниз; фоновые контексты создаются только в log sink, где вызывающего
  контекста нет.
- Пользовательские тексты бота — константы в начале файла-обработчика, не литералы по месту.
- Библиотечный пакет `github.com/go-telegram/bot/models` импортируется как `tgmodels`, чтобы не
  сталкиваться с `internal/models`.

## 10. Коммиты

- Формулировка: тип + суть изменения в повелительном наклонении (`feat: add ...`), без `wip`.
- В одном коммите — одна задача плана вместе с её тестами и обновлением `docs/plans/`.
